# In-cluster network segmentation

Status: **planned (2026-10-30)**. Nothing in this document is applied yet. Phases 1 and 2 are designed to be low-risk; phases 3 and 4 need the per-namespace allow-list work described below.

The tailnet is tag- and group-scoped (`docs/tailscale-acl-hardening.md`). The pod network is not: every namespace still has an allow-all ingress and egress path, so a compromised app can reach every datastore in the cluster.

## Why this is the next step

The controls that already exist (digest-pinned images, probes, resource limits, sealed secrets, pod hardening, PSS baseline) all assume a pod is either good or bad. The realistic compromise is a pod that is compliant with every policy and then runs attacker code — an upstream CVE in a `:latest`-tracking image, a malicious dependency, or a compromised Funnel endpoint. Nothing in the cluster contains that pod's blast radius today.

Seven policies in the whole cluster, all generated by upstream Argo CD's `install.yaml`, all scoped to Argo CD's own pods. There are 61 namespaces and 69 Services; the other 60 namespaces have no policy of any kind.

Policy enforcement itself is available: k3s runs kube-router's network policy controller, and `ansible/roles/k3s/templates/{init,server,agent}.yaml.j2` does not set `disable-network-policy`. A `NetworkPolicy` applied today is enforced.

### What a compromised pod can reach today

- Every datastore: `immich-postgres-service:5432`, `immich-valkey-service:6379`, `ente-postgres-service:5432`, `ente-garage-service:3900`, `miniflux-postgres-service:5432`, the linkding Postgres, every PVC-backed volume another pod has mounted.
- The identity provider: `pocket-id-app-service:80` (admin API included).
- The deployment system: `argocd-repo-server:8081` and `argocd-server:443`. `apps/project.yml` is `sourceRepos: ['*']`, `destinations: ['*']`, `clusterResourceWhitelist: ['*']`, and Argo CD is cluster-admin — so "write to the repo server" or "read its credentials" is equivalent to cluster ownership.
- Monitoring: `prometheus:9090` and `alertmanager:9093`, i.e. the evidence.
- The API server: `kubernetes.default.svc:443` from any pod, with whatever the default ServiceAccount token grants.

No lateral step is required for any of these. `curl` is enough.

## Traffic that has to keep working

Measured from the live cluster and from `gatus.yml`/`kustomization.yml`, not assumed.

| Source | Destination | Port | Why |
| --- | --- | --- | --- |
| namespace `tailscale` (`ingress-proxy-group-*`, `ts-consignment-app-funnel-ingress-*`, `ts-minecraft-app-service-*`) | every app pod | Service port | all tailnet, Funnel and `loadBalancerClass: tailscale` access |
| namespace `gatus` | `<app>-app-service.<ns>` | http | in-cluster health checks (`gatus.yml` uses ClusterIP DNS, not tailnet names) |
| app pod | its own datastore in the same namespace | 5432 / 6379 / 3900 | immich, ente, miniflux, linkding |
| `zigbee2mqtt` | `mosquitto` | 1883 | `mosquitto-app-service.mosquitto:1883` |
| home-assistant | `mosquitto` | 1883 | broker is configured in HA's UI, not in git |
| `prometheus` | `alertmanager` | 9093 | alert delivery |
| `pocket-id` | `smtp-relay` | 25 | admin login codes |
| every OIDC app | `tailscale/ts-idp-swkld` via the `idp` ExternalName | 443 | token/userinfo back-channel through `oidc-egress` |
| `prometheus` | kubelet/cadvisor on node IPs, apiserver, exporters | 10250 / 443 / 9100+ | metrics |
| `argocd`, `gatus`, `semaphore`, `healthchecks` | `kubernetes.default.svc` | 443 | API access |
| workloads that leave the cluster | internet | various | qbittorrent, syncthing, searxng, indexers, HA cloud, Immich push, Minecraft |

Two consequences worth stating up front:

- **Gatus is an in-cluster source, not a tailnet one.** Every `gatus.yml` in the repo targets `http://<app>-app-service.<ns>`, so `gatus` must be in the allow-list or the status page goes red.
- **OIDC does not go pod-to-pod.** Apps resolve `idp.beaver-cloud.ts.net` through the CoreDNS rewrite to the `idp` ExternalName, which the operator points at `ts-idp-swkld` (the `oidc-egress` proxy pods in `tailscale`). So an egress rule to the `tailscale` namespace on 443 covers every OIDC caller; `pocket-id` itself only receives from the ingress proxies.

## Findings

| # | Finding | Impact |
| --- | --- | --- |
| 1 | No default-deny ingress in any application namespace | Full pod-to-pod reachability, including all datastores |
| 2 | No egress policy anywhere | Exfiltration and API-server reachability are unconstrained |
| 3 | `home-assistant`, `omada`, `scrypted`, `syncthing` run `hostNetwork` with a `hostPort` | NetworkPolicy does not constrain a `hostNetwork` pod; these are node-level listeners |
| 4 | `jellyfin`, `makemkv` are `privileged` and mount host paths | A compromise is a node compromise, not a namespace one |
| 5 | Argo CD's own policies are the only ones, so the pattern exists but was never generalised | — |
| 6 | No security-oriented alerts (no policy-denial visibility) | Phase 1 breakage would be noticed only via Gatus |

Findings 3 and 4 are why those six app namespaces carry `enforce: privileged` in their own `app.yml` (the infrastructure components with the same problem are exempted the same way). Segmentation does not help them; their fix is separate (move `hostNetwork` services behind the ingress proxies).

## Target model

A shared component, the same pattern as `components/pod-hardening`, so the policy is written once and added per app with one line.

`components/network-policy/kustomization.yml`:

```yaml
---
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component

resources:
  - network-policies.yml
```

`components/network-policy/network-policies.yml`:

```yaml
---
# Deny everything not explicitly allowed below. All four policies select every
# pod in the namespace; NetworkPolicy ingress rules are additive, so the result
# is "deny by default, allow same-namespace, Gatus and the Tailscale proxies".
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: {}
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-monitoring
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: gatus
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-proxies
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: tailscale
```

Usage in an app, next to the existing components:

```yaml
components:
  - ../../components/pod-hardening
  - ../../components/app-tmp-dirs
  - ../../components/network-policy
```

`kubernetes.io/metadata.name` is set by the API server on every namespace (1.21+), so no namespace labels are needed.

### Cross-namespace exceptions

`default-deny-ingress` is per namespace, so any cross-namespace flow needs a policy on the **destination** namespace. The known ones:

| Destination namespace | Extra ingress rule |
| --- | --- |
| `mosquitto` | from `zigbee2mqtt` and `home-assistant`, port 1883 |
| `alertmanager` | from `prometheus`, port 9093 |
| `smtp-relay` | from `pocket-id`, port 25 |

These live in the destination app's `kustomization.yml` as a small `NetworkPolicy` resource, not in the shared component.

### Egress (phase 4 only)

Egress stays open until phase 4. When it lands, the high-value namespaces (`immich`, `ente`, `linkding`, `miniflux`, `pocket-id`, `sealed-secrets`, `argocd`, `prometheus`, `gatus`) get:

- UDP/TCP 53 to `kube-system` (CoreDNS),
- TCP 443 to `tailscale` (the OIDC egress proxies),
- same-namespace,
- TCP 443 to the apiserver for components that use a ServiceAccount (`argocd`, `gatus`, `prometheus`, `semaphore`).

Application namespaces with a genuine internet dependency are **not** in phase 4. Enumerating CDN endpoints for searxng or trackers for qbittorrent has poor cost/benefit, and the datastores are the prize.

## Rollout

| Phase | Change | Risk | Failure signature |
| --- | --- | --- | --- |
| 0 | This document, plus `components/network-policy` committed but unused | none | — |
| 1 | Component on `donetick` (single service, OIDC, in-cluster Postgres) and `linkding` (Postgres + OIDC) | low | Gatus `donetick`/`linkding` red; app login fails; Postgres unreachable |
| 2 | Component on the remaining `apps/*` namespaces | low | a Gatus check red, or an app that calls another app directly |
| 3 | Component on `platform/*` and `infrastructure/*`, with the exception policies above | medium | `zigbee2mqtt` stops publishing, alerts stop arriving, Pocket ID cannot send mail |
| 4 | Egress deny on the datastore and control-plane namespaces | medium | OIDC token calls time out; `sealed-secrets` cannot reach the API |

Order matters in phase 3: apply the exception policy in the same commit as the default-deny, otherwise `mosquitto`/`alertmanager`/`smtp-relay` go dark between syncs.

Rollback for any phase: remove the `- ../../components/network-policy` line, let Argo sync. No cluster state is created outside git.

## Verification

Prove the policy is enforced, not just present:

```sh
# from inside an app namespace, against another app's Service: must time out
kubectl -n donetick run netpol-canary --rm -it --image=curlimages/curl --restart=Never -- \
  curl -sS -m 3 http://radarr-app-service.radarr
```

Then confirm the legitimate paths still work: every Gatus check green, `zigbee2mqtt` publishing, an OIDC login completing (token **and** userinfo, i.e. the browser flow, not just the UI loading), an alert firing end to end, and Argo CD syncing.

`kubectl get netpol -A` should show four policies per segmented namespace plus the three exceptions. Each app's `namePrefix` is applied to the component's resources, so the names read `<app>-default-deny-ingress`, `<app>-allow-same-namespace`, `<app>-allow-monitoring` and `<app>-allow-ingress-proxies`.

## Caveats and open questions

- **`hostNetwork` pods are not segmented.** `home-assistant`, `omada`, `scrypted`, `syncthing` listen on node ports and are reachable from anywhere in the cluster regardless of policy. Either accept it or move them behind the ingress proxies (a separate project).
- **DNS is not denied in phases 1-3.** Ingress-only policies do not affect egress, so CoreDNS still resolves every Service in the cluster. Information disclosure via DNS is not addressed.
- **The kube-apiserver stays reachable in phases 1-3** for the same reason. Pods hold only default ServiceAccount tokens (no `automountServiceAccountToken: false`), so the exposure is discovery-level until phase 4.
- **Minecraft uses UDP 19132 and TCP 25565** via a `loadBalancerClass: tailscale` Service; its proxy pod is in `tailscale`, so `allow-ingress-proxies` covers it. Verify after phase 2.
- **Gatus checks the ClusterIP Service, not the ingress**, so `allow-monitoring` is required even for apps that are otherwise tailnet-only.
- **PSS interaction:** every Application sets `pod-security.kubernetes.io/*` on its own namespace through `spec.syncPolicy.managedNamespaceMetadata` — `enforce: baseline` (or `privileged`, with the reason in a comment) plus `warn`/`audit: restricted`. Argo applies it with server-side apply at sync time, so the auto-added `kubernetes.io/metadata.name` label survives; manual label drift is corrected on the next sync rather than by the diff engine. An app added to a segmented namespace inherits both; nothing in the component conflicts with PSS.
